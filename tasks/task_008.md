# Задача 008: Админ-панель управления пользователями

## 1. Цель
Реализовать административное управление пользователями: просмотр, создание, смена роли, блокировка/разблокировка и сброс пароля. Закрыть требование ТЗ «Управление пользователями» для роли `admin`.

## 2. Зависимости
- Выполнена Задача 001 (пользователи, роли, авторизация).
- Для production-сценариев сброса пароля — Задача 000 (SMTP, конфигурация).

## 3. Требования к реализации

### 3.1. Структура данных
Дополнить таблицу `users`:

- `is_blocked` (boolean, default: false) — признак блокировки;
- `blocked_at` (timestamp, nullable) — дата блокировки;
- `blocked_reason` (string, nullable) — причина блокировки;
- `version` (unsigned integer, default: 1) — уже добавлено в Задаче 001, используется для оптимистичной блокировки.

### 3.2. Права доступа
- Все маршруты `/admin/users*` доступны только роли `admin`.
- `UserPolicy`:
  - `viewAny`, `create`, `update`, `block`, `resetPassword` — только `admin`;
  - запрещено блокировать и понижать самого себя;
  - запрещено оставлять систему без активного администратора.
- `EnsureUserIsNotBlocked` проверяет `is_blocked` на каждом авторизованном запросе.
- Заблокированный пользователь не может войти; при наличии database-сессий — завершить их.

### 3.3. Функциональность
- **Список пользователей:** поиск по имени, фамилии, email; фильтр по роли и статусу; пагинация.
- **Создание пользователя:** имя, фамилия, email, роль. Пароль генерируется случайно и не показывается; пользователю отправляется стандартная ссылка сброса пароля.
- **Редактирование:** имя, фамилия, email, роль. Смена роли фиксируется в audit-логе.
- **Блокировка/разблокировка:** `is_blocked`, `blocked_at`, `blocked_reason`; блокировка self и последнего администратора запрещена.
- **Сброс пароля:** администратор инициирует стандартный Laravel password reset link; пароль в открытом виде не показывается и не хранится.
- **Audit:** события `user.created`, `user.role_changed`, `user.blocked`, `user.unblocked`, `user.password_reset_requested`.

### 3.4. Пользовательский интерфейс
- `admin/users/index` — таблица: ФИО, email, роль, статус, дата блокировки, действия.
- `admin/users/create`, `admin/users/edit` — формы с валидацией.
- Бейджи ролей и статусов; подтверждение блокировки и сброса пароля.
- Адаптивная верстка: таблица на десктопе, карточки на мобильных.

### 3.5. Валидация и конкурентность
- Email уникален; роль — только `guest`, `arbiter`, `admin`.
- Обновление пользователя — compare-and-swap по `version`; при конфликте `409`.
- Создание пользователя — транзакция только для записи в БД; письмо со ссылкой сброса отправляется после commit. При ошибке отправки пользователь остается созданным, администратор видит предупреждение и может отправить ссылку повторно.
- Rate limiting на сброс пароля и попытки входа.

## 4. Критерии приемки (DoD)
1. Администратор видит список пользователей с поиском и фильтрами.
2. Администратор может создать пользователя, изменить роль, заблокировать/разблокировать и инициировать сброс пароля.
3. Заблокированный пользователь не может войти и не проходит `EnsureUserIsNotBlocked`.
4. Нельзя заблокировать или понизить самого себя и оставить систему без активного администратора.
5. Пароль не отображается в открытом виде; сброс выполняется через стандартный password broker.
6. Все действия с ролями и блокировками попадают в audit-лог.
7. Судья и гость получают `403` на маршрутах `/admin/users*`.

## 5. Проверка и тесты
- Feature-тест: доступ к `/admin/users` только для `admin`; `arbiter` и `guest` получают `403`.
- Feature-тест: создание пользователя, смена роли, блокировка и разблокировка.
- Feature-тест: заблокированный пользователь не может войти.
- Feature-тест: запрет блокировки/понижения последнего администратора и самого себя.
- Feature-тест: запрос сброса пароля отправляет уведомление (fake mail).
- Feature-тест: конфликт версий при одновременном редактировании пользователя.

## 6. Риски и допущения

- Неверная проверка последнего администратора может заблокировать систему; правило покрывается тестами.
- Заблокированный пользователь с активной сессией должен быть отсечен middleware; при database-сессиях сессии удаляются.
- Доставка письма для сброса пароля зависит от SMTP; при ошибке администратор должен увидеть понятное сообщение.
- Смена роли не должна позволять privilege escalation; все проверки — на сервере, не только в UI.
- Удаление пользователей не входит в обязательный объем; предпочтительна блокировка, чтобы не разрушать аудит.
- Предполагается, что роли взаимоисключающие.

## 7. Открытые вопросы

- Должны ли администраторы удалять пользователей или только блокировать?
- Нужно ли одобрение регистрации новых пользователей?
- Должна ли смена роли принудительно завершать сессии пользователя?
- Требуется ли подтверждение email?
- Разрешать ли администратору задавать временный пароль вручную или только отправлять reset link?
- Что делать с турнирами заблокированного судьи — переназначать другому судье или оставлять как есть?
