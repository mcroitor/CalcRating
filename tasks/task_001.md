# Задача 001: Инициализация проекта, БД SQLite и авторизация с ролевой моделью

## 1. Цель
Развернуть базовый каркас приложения на Laravel с базой данных SQLite, настроить систему аутентификации и разграничения прав доступа на основе ролей: Гость, Судья, Администратор.

## 2. Зависимости
- Нет (первая задача).

## 3. Требования к реализации

### 3.1. Стек и инфраструктура
- Laravel 12.x на PHP 8.4+; проверено на PHP 8.4.19.
- Composer 2.x.
- СУБД: SQLite 3 (файл `database/database.sqlite`), расширения `pdo_sqlite` и `sqlite3`.
- SQLite: `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=NORMAL`.
- Фронтенд-стартер: Laravel Breeze (Blade + Tailwind CSS + Vite).
- Node.js 20+ / npm 10+ — только для сборки фронтенда. На production Node.js не требуется.
- Обязательные расширения PHP: `pdo_sqlite`, `sqlite3`, `mbstring`, `dom`, `xml`, `zip`, `gd`, `intl`, `fileinfo`, `curl`, `openssl`.

### 3.2. Модель пользователей и роли
- Таблица `users`:
  - `id` (bigint, PK)
  - `name` (string) — имя
  - `surname` (string) — фамилия
  - `email` (string, unique)
  - `password` (string)
  - `role` (string/enum: `guest`, `arbiter`, `admin`, по умолчанию `guest`)
  - `version` (unsigned integer, default: 1) — версия для оптимистичной блокировки
  - `timestamps`
- Концепция ролей:
  - **Гость:** неавторизованный пользователь (публичный просмотр) или зарегистрированный пользователь с ролью `guest`.
  - **Судья (Менеджер турнира):** роль `arbiter` — создание турниров, добавление игроков, жеребьевка, внесение результатов.
  - **Администратор:** роль `admin` — полные права, включая управление пользователями и удаление турниров.
- Seeder: создание базового администратора (`admin@example.com`) и тестового судьи (`arbiter@example.com`).

### 3.3. Разграничение доступа (Middleware / Policy)
- Реализовать Middleware проверки роли `EnsureUserHasRole` и Policy/Gate для проверки прав на конкретные действия. Имя `RoleMiddleware` не используется.
- Гости имеют доступ к публичным страницам (просмотр списков).
- Действия мутации (создание, редактирование, удаление, импорт/экспорт) закрыты для неавторизованных пользователей.
- Административная панель/маршруты управления пользователями доступны только `admin`.

### 3.4. Подзадачи реализации
- [x] **1.1. Инициализация каркаса:** Установка Laravel, переключение на SQLite (`database.sqlite`), настройка WAL/`busy_timeout`/`foreign_keys`, базовая конфигурация `.env`.
- [x] **1.2. Расширение модели User:** Миграция добавления полей `surname`, `role` (enum: `guest`, `arbiter`, `admin`) и `version`, настройка `$fillable` и кастов.
- [x] **1.3. Стартовый пакет аутентификации:** Развертывание Laravel Breeze (Blade + Tailwind), проверка регистрации, входа, сброса пароля и выхода.
- [x] **1.4. Middleware и авторизация:** Реализация проверки ролей через Middleware (`EnsureUserHasRole`) и Policy/Gates; регистрация seeder с тестовыми учетными записями (`admin`, `arbiter`).
- [x] **1.5. Тестирование доступа:** Написание Feature-тестов на доступность публичных и защищенных маршрутов по ролям.
- [x] **1.6. Сборка фронтенда:** Проверка установки npm-зависимостей (`npm install`, далее `npm ci` при наличии `package-lock.json`) и сборки `npm run build`; результат сборки попадает в `public/build`, production-запуск не требует Node.js. При отсутствии Node.js на целевой площадке сборка выполняется в CI или локально, а `public/build` доставляется вместе с приложением.

## 4. Критерии приемки (DoD)
1. Проект поднимается локально через `php artisan serve`.
2. База данных SQLite автоматически инициализируется и наполняется начальными сидами (`php artisan migrate --seed`).
3. Доступны регистрация, вход, восстановление пароля и выход из системы.
4. Неавторизованный пользователь перенаправляется на форму входа; аутентифицированный пользователь с ролью `guest` при попытке закрытого действия получает `403 Forbidden`.
5. Судья и Администратор успешно проходят авторизацию и получают соответствующие права.
6. Команда `npm install && npm run build` (или `npm ci && npm run build` при наличии `package-lock.json`) завершается без ошибок, в `public/build` появляются manifest и собранные ассеты; для production-запуска Node.js не требуется.

## 5. Проверка и тесты
- Feature-тесты авторизации и регистрации (`tests/Feature/AuthTest.php`).
- Feature-тест проверки доступности маршрутов для разных ролей (Гость, Судья, Админ).
- Spike-тест конкурентной записи SQLite: два параллельных обновления одного агрегата не теряют данные, устаревшая версия возвращает `409` (главный технический риск проекта).

## 6. Риски и допущения

- Совместимость Laravel 12 / Breeze с PHP 8.4 зависит от версий пакетов; версии фиксируются в `composer.lock`.
- Файл SQLite может отсутствовать или быть недоступным для записи; приложение должно выдавать понятную ошибку, а не `500` без контекста.
- Сиды `admin@example.com` и `arbiter@example.com` предназначены только для разработки; в production они должны быть заменены или отключены.
- Роль `guest` по умолчанию означает, что новый зарегистрированный пользователь получает только чтение; это может быть неочевидно для пользователей.
- Сборка Vite требует Node.js; production использует заранее собранный `public/build`.
- Предполагается, что роли взаимоисключающие и у пользователя ровно одна роль.
