# Задача 004: Модуль управления турнирами и участниками

## 1. Цель
Создать модели, миграции и пользовательский интерфейс для ведения турниров, регистрации участников из реестра шахматистов, фиксации их стартового рейтинга, выбора режима расчета рейтинга и отображения турнирной информации.

## 2. Зависимости
- Выполнены Задачи 001 и 002 (модели пользователей, ролей и шахматистов).

## 3. Требования к реализации

### 3.1. Структура данных
- Таблица `tournaments`:
  - `id` (bigint, PK)
  - `arbiter_id` (bigint, fk к `users`) — судья/менеджер турнира
  - `name` (string) — название турнира
  - `pairing_type` (enum: `round_robin`, `swiss`, `olympic`) — тип жеребьевки
  - `rating_mode` (enum: `average`, `per_game`, default: `average`) — режим расчета рейтинга: по среднему рейтингу соперников или по каждой партии
  - `rounds_count` (integer) — количество туров
  - `games_per_round` (integer, default: 1) — партий в туре между парой соперников
  - `start_date` (date) — дата начала
  - `end_date` (date, nullable) — дата окончания
  - `location` (string, nullable) — место проведения
  - `notes` (text, nullable) — дополнительная информация
  - `status` (enum: `draft`, `in_progress`, `completed`, default: `draft`)
  - `version` (unsigned integer, default: 1) — версия для оптимистичной блокировки
  - `timestamps`
- Таблица `tournament_participants`:
  - `id` (bigint, PK)
  - `tournament_id` (bigint, fk к `tournaments`, cascade on delete)
  - `player_id` (bigint, fk к `players`, cascade on delete)
  - `points` (decimal 4,1, default: 0.0) — набранные очки
  - `rating_before` (integer) — рейтинг игрока на момент старта турнира; в `draft` хранится предварительное значение, окончательно фиксируется при переходе в `in_progress`
  - `rating_after` (integer, nullable) — рейтинг после завершения турнира
  - `version` (unsigned integer, default: 1) — версия для оптимистичной блокировки
  - Unique constraint: `[tournament_id, player_id]`

### 3.2. Логика и права доступа
- **Создание турнира:** доступно `arbiter` и `admin`. Поле `arbiter_id` заполняется текущим пользователем (или выбирается из списка судей администратором).
- **Режим расчета рейтинга:** выбирается при создании турнира (`average` или `per_game`), по умолчанию `average`. После старта турнира изменение запрещено.
- **Регистрация участников:**
  - Добавление шахматистов из общего реестра в турнир (пока турнир в статусе `draft`).
  - При добавлении участника его `rating_before` предварительно копируется из `players.current_rating`; до старта значение может обновляться.
- **Старт турнира:** переход `draft → in_progress` доступен `arbiter` и `admin`. При переходе в одной транзакции значения `rating_before` всех участников обновляются до актуальных и фиксируются; версии турнира и участников увеличиваются. После старта поле и состав участников не изменяются.
- **Конкурентные изменения:** обновление турнира и состава выполняется с проверкой `version` (compare-and-swap); при конфликте — `409 Conflict` и сообщение «Данные изменились, обновите страницу».
- **Просмотр:**
  - Список турниров с фильтрами по статусу, дате и типу жеребьевки доступен всем (включая гостей).
  - Карточка турнира: общие сведения, режим расчета рейтинга, состав участников, текущая турнирная таблица.
- **Удаление турнира:**
  - Доступно **только** роли `admin`.
  - Турнир в статусе `completed` удаляется только после подтверждения; записи `ratings` сохраняются, ссылка `ratings.tournament_id` обнуляется (`ON DELETE SET NULL`), см. `questions.md` №9.

### 3.3. Пользовательский интерфейс
- Форма создания/редактирования турнира с валидацией дат и параметров туров.
- Выбор режима расчета рейтинга: «По среднему рейтингу соперников» (`average`) или «По каждой партии» (`per_game`).
- Экран состава турнира: удобный выбор участников с поиском по фамилии.
- Индикаторы статуса турнира (Черновик, Идет, Завершен).
- Адаптивная турнирная таблица (место, ФИО, стартовый рейтинг, очки).
- Сортировка турнирной таблицы детерминирована: очки ↓ → личная встреча (только при равенстве двух участников и завершенной встрече с победителем) → число побед ↓ → стартовый рейтинг ↓ → ID шахматиста ↑. При равенстве трех и более участников личная встреча не применяется.
- Для олимпийской системы места определяются стадией выбывания; сортировка по очкам применяется только внутри группы участников, выбывших на одном раунде.

## 4. Критерии приемки (DoD)
1. Судья и Администратор могут создать турнир и добавить в него шахматистов.
2. При старте турнира в поле `rating_before` фиксируется актуальный рейтинг участника; после старта значение не изменяется.
3. Гость может открывать страницу списка турниров и просматривать детали любого турнира.
4. Кнопка и действие удаления турнира доступны исключительно администратору; судья получает 403 при попытке удалить турнир.
5. Нельзя добавить одного и того же шахматиста в турнир дважды.
6. Турнирная таблица сортируется детерминированно по цепочке tiebreak; при равенстве двух и трех участников порядок стабилен и не зависит от порядка выборки из БД.
7. Режим расчета рейтинга выбирается при создании турнира, сохраняется в БД и не может быть изменен после старта.
8. При конкурентном изменении состава или параметров турнира второе сохранение возвращает `409` и не перезаписывает данные.

## 5. Проверка и тесты
- Feature-тест проверки прав на создание (судья/админ) и удаление (только админ).
- Unit-тест: предварительная фиксация `rating_before` при добавлении и обновление до актуального при старте турнира; неизменность после старта.
- Unit-тест: детерминированный tiebreak при равенстве двух и трех участников.
- Feature-тест: выбор режима расчета сохраняется; изменение `rating_mode` после старта запрещено.
- Feature-тест: удаление завершенного турнира доступно только администратору; записи `ratings` сохраняются, `tournament_id` обнуляется.
- Feature-тест: конфликт версий при одновременном изменении состава турнира.

## 6. Риски и допущения

- Обновление `rating_before` при старте может изменить предварительные значения, которые видел судья; это документируется в UI.
- Конкурентное добавление участников защищено уникальным индексом и `version`, но требует понятного сообщения пользователю.
- Удаление завершенного турнира доступно только администратору и требует подтверждения; история рейтингов сохраняется, ссылка `ratings.tournament_id` обнуляется.
- Даты турнира валидируются с учетом часового пояса приложения; `end_date` не может быть раньше `start_date`.
- `rating_mode` фиксируется после старта; смена режима в `draft` допустима, так как результаты еще не вводятся.
- Предполагается, что состав участников фиксируется на старте и не меняется до завершения турнира.
- После старта запрещены изменения `rating_mode`, `pairing_type`, `rounds_count` и `games_per_round`; название, даты, место и примечания остаются редактируемыми без отдельного аудита (см. открытый вопрос ниже).
- Компаратор tiebreak реализован полностью (очки, личная встреча для двух участников, победы, стартовый рейтинг, ID). Число побед и результат личной встречи появляются в данных после Задачи 005, когда создается таблица `pairings`; до этого соответствующие шаги нейтральны и не влияют на порядок.

## 7. Открытые вопросы

- Можно ли добавлять участников после старта турнира? Текущее допущение — нет.
- Можно ли менять даты, место и регламент после старта? Текущее поведение: название, даты, место и примечания редактируются, структурные параметры турнира — нет; отдельный аудит не ведется.
- Есть ли максимальное количество участников? Ограничение не введено.
- Нужны ли командные турниры или только личные?
