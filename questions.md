# Вопросы перед началом реализации проекта

Документ фиксирует развилки архитектуры, окружения и бизнес-логики, которые необходимо утвердить до начала написания кода.

### 1. Связь «Пользователь» $\leftrightarrow$ «Шахматист»
* **Контекст:** В ТЗ разделены сущности «Пользователь» (логин, пароль, роль) и «Шахматист» (ФИО, дата рождения, рейтинг).
* **Вопрос:** Шахматисты — это отдельный справочник игроков, который ведут судьи (без логина), или зарегистрированный пользователь должен быть связан с конкретным шахматистом?
* **Варианты решения:**
  * **Вариант А (Рекомендуется):** Без связи. Шахматисты — только спортивный реестр под управлением судей. Личные кабинеты шахматистам не создаются.
  * **Вариант Б:** Добавить в `players` опциональное поле `user_id`, позволяющее пользователю привязать свой профиль к карточке игрока.

### 2. Сборка фронтенда: Node.js/Vite vs CDN
* **Контекст:** ТЗ требует адаптивный интерфейс (Laravel) и график изменения рейтинга (Chart.js).
* **Вопрос:** Доступен ли в целевом окружении Node.js/NPM для сборки ассетов?
* **Варианты решения:**
  * **Вариант А (Рекомендуется, если есть Node.js):** Стандартный стек Laravel Breeze (Tailwind CSS + Vite + Chart.js через npm).
  * **Вариант Б (Минимум зависимостей):** Tailwind CSS и Chart.js подключаются через CDN. Сборщик Vite исключается, проект запускается исключительно средствами PHP (`php artisan serve`).

### 3. Определение мест при равенстве очков в турнире
* **Контекст:** В шахматах участники часто набирают одинаковое количество очков.
* **Вопрос:** Требуется ли расчет сложных дополнительных коэффициентов FIDE (Бухгольц, Зоннеборн-Бергер, число побед) для ранжирования в таблице?
* **Варианты решения:**
  * **Вариант А (Рекомендуется):** Упрощенная сортировка: `Очки` $\to$ `Результат личной встречи` (только при равенстве двух участников) $\to$ `Число побед` $\to$ `Стартовый рейтинг` $\to$ `ID`.
  * **Вариант Б:** Полноценный расчет коэффициента Бухгольца (для швейцарской системы) и Зоннеборна-Бергера (для круговой системы).

### 4. Параллельное участие шахматиста в нескольких турнирах
* **Контекст:** Игрок может быть заявлен в два параллельно идущих турнира.
* **Вопрос:** Как фиксировать и пересчитывать рейтинг, если турниры пересекаются по времени?
* **Варианты решения:**
  * **Вариант А (Рекомендуется):** При старте турнира фиксируется моментальный рейтинг (`rating_before`); в `draft` допускается предварительное значение. Пересчет и запись нового рейтинга происходят в момент закрытия турнира тем турниром, который завершился раньше.
  * **Вариант Б:** Запретить игроку участвовать в новом турнире, пока не закрыт предыдущий незавершенный турнир с его участием.

### 6. Режимы расчёта рейтинга Elo
* **Контекст:** Формула Elo из ТЗ использует средний рейтинг соперников; для точного расчёта ожидаемых очков нужны очки по каждой партии.
* **Вопрос:** Один режим расчёта или два, и на каком уровне выбирается?
* **Варианты решения:**
  * **Вариант А (Рекомендуется):** Два режима — `average` (по умолчанию, соответствует формуле ТЗ) и `per_game`; выбор при создании турнира, после старта — нельзя.
  * **Вариант Б:** Только `average`, как в исходной формуле ТЗ.

### 7. Конкурентная запись в SQLite
* **Контекст:** SQLite допускает только одного писателя; несколько судей могут одновременно вносить результаты, менять состав и закрывать турниры.
* **Вопрос:** Как защититься от потери обновлений и как сообщать пользователю о конфликте?
* **Варианты решения:**
  * **Вариант А (Рекомендуется):** WAL, `busy_timeout`, короткие транзакции и оптимистичные версии; конфликт — HTTP `409`.
  * **Вариант Б:** Единая очередь записи / глобальная блокировка на время изменений.

### 1. Связь «Пользователь» ↔ «Шахматист»

**Решение: Вариант А — без связи.**

- `players` — самостоятельный спортивный реестр, поле `user_id` не добавляется.
- Личные кабинеты шахматистов не создаются; карточка `/players/{id}` доступна публично.
- Роли остаются прежними: `guest` (только чтение), `arbiter`, `admin`.
- Зарегистрированный пользователь с ролью `guest` и анонимный посетитель имеют одинаковые права на чтение.
- Если в будущем появится требование личного кабинета, поле `user_id` добавляется отдельной миграцией как nullable с уникальным индексом; текущая модель от этого не зависит.

### 2. Сборка фронтенда

**Решение: Вариант А — Laravel Breeze + Tailwind CSS + Vite, Chart.js через npm.**

- Node.js и npm используются только на этапе сборки ассетов; production-серверу достаточно PHP.
- Целевые версии: Node.js 20+ / npm 10+. На машине разработчика: Node.js 24.14.0, npm 11.21.2.
- Chart.js устанавливается как npm-зависимость и импортируется в `resources/js/app.js`; CDN не используется.
- Первичная установка зависимостей — `npm install`; после появления `package-lock.json` используется `npm ci`. Сборка — `npm run build`, результат попадает в `public/build`.
- Если целевая площадка не имеет Node.js, сборка выполняется в CI или локально, а `public/build` доставляется вместе с приложением.
- CDN-вариант допускается только как аварийный fallback при невозможности организовать сборку.

### 3. Определение мест при равенстве очков

**Решение: Вариант А — упрощенная сортировка без Бухгольца и Зоннеборна-Бергера.**

Детерминированная цепочка tiebreak:

1. Набранные очки — по убыванию.
2. Результат личной встречи — только если ровно два участника делят место и их встреча завершена с победителем.
3. Число побед — по убыванию.
4. Стартовый рейтинг (`rating_before`) — по убыванию.
5. ID шахматиста — по возрастанию (для стабильности порядка).

Дополнительно:

- При равенстве трех и более участников личная встреча не применяется, так как не дает однозначного порядка; используются число побед, стартовый рейтинг и ID.
- Для олимпийской системы места определяются стадией выбывания; сортировка по очкам применяется только внутри группы участников, выбывших на одном раунде.
- Бухгольц и Зоннеборн-Бергер не входят в MVP. При необходимости добавляются позже в сервис подсчета без изменения схемы БД.

### 4. Параллельное участие в нескольких турнирах

**Решение: Вариант А — параллельное участие разрешено, рейтинг фиксируется снапшотом.**

- В статусе `draft` поле `rating_before` может показывать текущий рейтинг как предварительное значение.
- Перед переводом турнира в `in_progress` значения `rating_before` всех участников обновляются до актуальных и фиксируются одной транзакцией. После старта поле не изменяется.
- При завершении турнира расчет `R'` выполняется от `rating_before`, после чего в одной транзакции обновляются `rating_after`, `players.current_rating`, создается запись в `ratings` и турнир переводится в `completed`.
- Турниры закрываются в фактическом порядке завершения: завершившийся раньше записывает рейтинг раньше.
- Перед закрытием турнира проверяется, что `players.current_rating` совпадает с `rating_before` участника. Если рейтинг изменился из-за другого завершенного турнира, судье выводится предупреждение, а факт расхождения фиксируется в журнале. Значения дельт при этом не суммируются: `current_rating` остается равным `R'` последнего завершенного турнира, как требует ТЗ.
- Запрет параллельного участия (Вариант Б) не применяется.
- Если позже потребуется точный суммарный пересчет пересекающихся турниров, используется модель рейтинговых периодов; это отдельная итерация вне MVP.

### 5. Версия PHP и поддержка БД

### 6. Режимы расчета рейтинга

**Решение: два режима, выбираемые на уровне турнира.**

- `average` — по среднему рейтингу соперников. Режим по умолчанию, соответствует исходной формуле ТЗ.
- `per_game` — по каждой партии. Ожидаемые очки считаются для каждой партии отдельно и суммируются.

В обоих режимах:

- $R_{before}$ — рейтинг игрока на старте турнира; используется для всех партий, порядок партий не влияет на результат;
- $R_{opp\_before}^{(i)}$ — рейтинг соперника в партии $i$ на старте турнира;
- $N$ — количество завершенных партий против реальных соперников;
- $S$ — фактически набранные очки;
- $K$ — коэффициент по общим правилам (возраст, стаж, рейтинг);
- bye, партии со статусом `*` и партии `0-0` (обоюдная неявка) в расчет рейтинга не включаются;
- при `games_per_round = 2` каждая партия учитывается отдельно.

**Режим `average`:**

$$R_{avg} = \frac{1}{N} \sum_{i=1}^{N} R_{opp\_before}^{(i)}$$

$$E = \frac{N}{1 + 10^{(R_{avg} - R_{before})/400}}$$

$$R' = \operatorname{round}(R_{before} + K \cdot (S - E))$$

**Режим `per_game`:**

$$E_i = \frac{1}{1 + 10^{(R_{opp\_before}^{(i)} - R_{before})/400}}$$

$$E = \sum_{i=1}^{N} E_i, \qquad S = \sum_{i=1}^{N} S_i$$

$$R' = \operatorname{round}(R_{before} + K \cdot (S - E))$$

где $S_i = 1$ при победе, $0.5$ при ничьей и $0$ при поражении.

Реализация:

- В таблицу `tournaments` добавляется поле `rating_mode` (enum: `average`, `per_game`, default: `average`).
- Режим выбирается при создании турнира и фиксируется; после старта турнира изменение запрещено.
- `EloCalculationService` поддерживает оба режима; `CompleteTournamentAction` использует режим текущего турнира.
- В шапке экспортируемого протокола указывается режим расчета.
- Тесты: оба режима на одном наборе партий, проверка различия результатов из-за нелинейности формулы, проверка `N = 0`, bye и `0-0`.

### 7. Конкурентная запись в SQLite

**Решение: WAL + короткие транзакции + оптимистичные версии для критичных агрегатов.**

Контекст: несколько судей могут одновременно вносить результаты, менять состав турнира или закрывать турнир. SQLite допускает только одного писателя.

Варианты:

- **Вариант А (Рекомендуется):** WAL, `busy_timeout`, короткие транзакции и оптимистичные версии для изменяемых агрегатов. При конфликте — `409 Conflict` и просьба обновить данные.
- **Вариант Б:** единая очередь записи / глобальная блокировка на время изменений. Проще, но ограничивает параллельную работу судей.

Правила:

- Включить `journal_mode=WAL`, `busy_timeout=5000`, `foreign_keys=ON`, `synchronous=NORMAL`.
- Все многошаговые изменения выполнять в `DB::transaction()`; транзакции короткие, без внешних вызовов (mail, PDF, HTTP) внутри.
- Не полагаться на `lockForUpdate()`: в SQLite нет построчных блокировок.
- Для изменяемых агрегатов используется поле `version` (unsigned integer, default 1): `users`, `players`, `tournaments`, `tournament_participants`, `pairings`.
- Обновление выполняется как compare-and-swap: `WHERE id = ? AND version = ?`, затем `version = version + 1`. Если затронуто 0 строк — это конфликт.
- Конфликт выбрасывает `ConcurrentModificationException` и возвращает HTTP `409` с сообщением «Данные изменились, обновите страницу»; факт пишется в лог.
- Для вставок используются уникальные индексы (`users.email`, `tournament_participants[tournament_id, player_id]`) и обработка `QueryException` (`409`/`422`).
- Закрытие турнира: в транзакции повторно проверяются статус, отсутствие `*`, версия турнира и версии участников; при расхождении — откат.
- Импорт: чанки по 100–500 строк, каждая в своей транзакции; повторный импорт не должен создавать дубликаты (правило дедупликации — `task_003`).
- Резервное копирование SQLite — через `.backup` или `VACUUM INTO`, а не копированием файла на работающей БД.

Вариант Б не применяется: он неоправданно ограничивает работу судей; WAL + версии достаточны для небольшого приложения.

### 8. Целевая архитектура приложения: слои, границы, ошибки, маршруты

**Решение: Вариант А — архитектура фиксируется централизованно в `technical.md` и отражается здесь; изменения идут по процедуре §11 `PIPELINE.md`.**

Слои и направление зависимостей:

- HTTP → Application → Domain/Persistence → SQLite. Обратных зависимостей нет.
- **Controllers:** приём запроса, валидация через Form Request, проверка права через Policy/Gate, вызов Service/Action, возврат ответа. Бизнес-логики, Elo и многошаговых транзакций в контроллерах нет.
- **Services/Actions:** вся бизнес-логика. Не зависят от HTTP-слоя: `request()`, `response()`, `view()` не используются.
- **Models:** связи, касты, scopes, небольшие инварианты. Сценарии и транзакции — не в моделях.
- **Blade:** только отображение; запросов к БД и расчётов в шаблонах нет.
- **Middleware:** аутентификация, роли, блокировка пользователя, `request_id`. Права проверяются только через Policy/Gate и middleware, а не скрытием кнопок.

Транзакции и конкурентность:

- Многошаговые изменения — `DB::transaction()` внутри Service/Action; транзакции короткие; почта, PDF и HTTP-вызовы — вне транзакции.
- Оптимистичная блокировка через поле `version` (`users`, `players`, `tournaments`, `tournament_participants`, `pairings`): compare-and-swap `WHERE id = ? AND version = ?`, затем `version = version + 1`.
- Конфликт версий → `ConcurrentModificationException` → HTTP `409` с сообщением «Данные изменились, обновите страницу»; факт пишется в лог.
- `lockForUpdate()` не используется: в SQLite нет построчных блокировок.

Ошибки и логирование:

- Коды ответа: `422` — валидация, `403` — доступ, `404` — отсутствующая сущность, `409` — конфликт версий и нарушение уникальности.
- `request_id` проставляется middleware `AssignRequestId`, в каждый лог попадает через `Log::withContext()`.
- Каналы: `stack`/`daily` — приложение, `audit` — доменные события (см. №12).

Маршруты и имена:

- Карта маршрутов — источник истины для URL; фиксируется в `technical.md` §«Карта маршрутов».
- Имена классов из каталога `technical.md` обязательны: `EnsureUserHasRole` (не `RoleMiddleware`), `ImportPlayersAction`, `StandingsService`, `PlayersExport`, `TournamentExport`, `RoundRobinGenerator`/`OlympicGenerator`/`SwissGenerator`.
- Статические сегменты (`create`, `import`, `export`) регистрируются в `routes/web.php` раньше параметрических.

### 9. Удаление шахматиста и целостность рейтинговой истории

**Решение: Вариант А — удаление шахматиста ограничено; рейтинговая история неизменяема.**

- История рейтингов неизменяема: записи в `ratings` не редактируются и не удаляются вручную.
- Начальная запись `ratings`, создаваемая при регистрации шахматиста, является базовой точкой и не считается турнирной историей. Турнирной историей считается любая другая запись, в том числе запись, у которой `tournament_id` стал `NULL` после удаления турнира.
- Удаление шахматиста запрещено, если:
  - есть турнирная рейтинговая история (записей `ratings` больше одной или единственная запись имеет `tournament_id IS NOT NULL`), или
  - шахматист участвует в турнире в статусе `in_progress` или `completed`.
- Удаление разрешено, если записей `ratings` нет или есть только начальная запись с `tournament_id IS NULL`, а участие — только в турнирах в статусе `draft`. В одной транзакции удаляются начальная запись, участие в `draft` и сам шахматист.
- Внешние ключи: `ratings.player_id` — `ON DELETE RESTRICT`, `ratings.tournament_id` — `ON DELETE SET NULL`, `tournament_participants.player_id` — `ON DELETE CASCADE`.
- Удаление турнира в статусе `completed` доступно только `admin` и требует подтверждения; записи `ratings` при этом сохраняются, ссылка на турнир обнуляется.
- Проверка выполняется в Policy и в сервисе; интерфейс показывает причину запрета, а не только скрывает действие.
- Вариант Б (каскадное удаление вместе с историей) не применяется: он уничтожает аудит рейтингов, который ТЗ требует сохранять.
- Мягкое удаление (`deleted_at`) и блокировка шахматиста — вне MVP; при необходимости оформляются отдельной задачей.

### 10. Язык интерфейса и данных

**Решение (пересмотрено 2026-11-16): Вариант Б — мультиязычный интерфейс, `en` по умолчанию и `ru` вторым языком.**

- Поддерживаемые локали — `en` (по умолчанию) и `ru`; список хранится в `config/locales.php` (`supported`). Новая локаль добавляется файлами `lang/<locale>/` и `lang/<locale>.json` без правок кода.
- `APP_LOCALE=en`, `APP_FALLBACK_LOCALE=en`; отсутствующий ключ `ru` отдаёт английскую строку, страница не падает.
- Язык выбирается middleware `SetLocale`: сессия → cookie (`locale`, 1 год) → `en`. Префикс языка в URL не используется; переключатель `EN | RU` доступен гостю и авторизованному пользователю.
- Строки интерфейса, валидации, flash-сообщений, ошибок, писем и подписей PDF/HTML — в `lang/en` и `lang/ru`; устаревший путь `resources/lang` не используется, актуальный — `lang/`.
- Пользовательские данные (ФИО, названия турниров, примечания) не переводятся. Машинные значения (статусы, `average`/`per_game`, коды ошибок, заголовки XLSX/CSV, audit-логи) остаются латиницей.
- Даты форматируются по локали; расчёты, рейтинги и права от языка не зависят.
- `users.locale` не вводится: письма уходят на языке инициатора действия — ограничение, вынесенное в открытые вопросы `task_009`.
- HTML-ответы зависят от cookie, поэтому прокси/CDN не кэширует HTML без `Vary: Cookie`.
- Пересмотр отменяет прежнее решение «русский единственный в MVP»; реализация — `task_009`.

### 11. Импорт шахматистов: атомарность и частичный успех

**Решение: Вариант А — частичный успех, чанковая обработка.**

- Импорт разбивается на чанки по 100–500 строк; каждый чанк обрабатывается в своей транзакции.
- Строки, не прошедшие валидацию (формат даты, пустые обязательные поля), отбрасываются и попадают в отчёт; титул по умолчанию — `None`, рейтинг по умолчанию — `1000`.
- Ошибка уровня БД (нарушение уникальности, конфликт версии) откатывает текущий чанк и останавливает импорт; ранее загруженные чанки сохраняются.
- Дубликаты определяются по `last_name + first_name + birth_date`; существующий игрок не изменяется, строка попадает в отчёт как предупреждение.
- Отчёт пользователю: «Успешно импортировано: N, с ошибками: M» плюс список строк с причинами.
- Вариант Б (всё-или-ничего) не применяется: файл на 5000+ строк удерживал бы блокировку записи SQLite на всё время обработки.

### 12. Audit-лог: хранение и срок хранения

**Решение: Вариант А — отдельный файловый канал, без таблицы в БД.**

- Audit-события пишутся в отдельный Log-канал `audit` (файлы `storage/logs/audit-YYYY-MM-DD.log`), а не в таблицу БД: аудит не должен раздувать базу и не должен блокировать запись SQLite.
- Минимальный набор событий: `user.created`, `user.role_changed`, `user.blocked`, `user.unblocked`, `user.password_reset_requested`, `tournament.completed`, `rating.changed`, `players.imported`.
- Формат записи — JSON: `timestamp`, `event`, `actor_id`, `target_type`, `target_id`, `request_id`, `context`.
- Retention — 90 дней; ротация и очистка — в `task_000`, бэкап audit-логов не делается.
- Просмотр журнала в UI не входит в MVP; при необходимости — отдельная задача с таблицей `audit_logs`.
- Вариант Б не применяется: таблица в SQLite конкурирует с основной записью и требует миграции, не нужной для MVP.

### 13. Первичная учётная запись администратора (bootstrap) и демо-сиды

**Решение: Вариант А — разделение dev-сидов и production CLI-bootstrap.**

- В локальной разработке и автотестах `DatabaseSeeder` создаёт демонстрационных пользователей с паролем `password`: `admin@example.com` (`admin`), `arbiter@example.com` (`arbiter`), `guest@example.com` (`guest`), которые явно документируются в `README.md`.
- При `APP_ENV=production` вызов `DatabaseSeeder` завершается исключением (`RuntimeException`), исключая случайное попадание стандартного пароля `password` и демо-турниров в боевую базу.
- Для создания первого администратора на чистой базе используется команда `php artisan admin:bootstrap {email} {--name=Admin} {--surname=Administrator} {--send-reset} {--promote}` (логика в `App\Actions\BootstrapAdminAction`):
  - с флагом `--send-reset` создаётся учётная запись со случайным паролем и отправляется ссылка установки пароля на email (вне транзакции БД);
  - без `--send-reset` пароль запрашивается через скрытый интерактивный ввод (`secret()`) с подтверждением и проверкой `Password::defaults()` — пароль не передаётся аргументом CLI и не попадает в историю командной оболочки или `.env`;
  - если пользователь с указанным `email` уже существует, изменение выполняется только при явном флаге `--promote` через `updateWithVersion` (с повышением роли до `admin` и разблокировкой при необходимости);
  - операция записывает событие `admin.bootstrapped` в канал `audit`.
- Вариант Б не применяется: хранение `ADMIN_PASSWORD` в `.env` оставляет открытый пароль на диске после инициализации.

### 14. Шахматные клубы, клубное членство и группировка турниров

**Решение: Вариант А — клубы с клубным штатом (`club_user`), множественным членством игроков (`club_player`) и обязательной привязкой турниров (`tournaments.club_id`) при едином реестре и едином рейтинге Elo.**

- **Сущность `Club` (`clubs`):** представляет шахматный клуб или шахматную организацию; поля `name` (уникальное), `code` (nullable, уникальный), `city`, `address`, `website`, `description`, `logo_path` (растровые `jpg`/`jpeg`/`png`/`webp` до 2 МБ на диске `public`, без `svg`), `status` (`active` / `archived`), `version` (оптимистичная блокировка).
- **Жизненный цикл клуба:** создавать, архивировать/восстанавливать, удалять клубы и назначать менеджеров может только глобальный `admin`. Удаление клуба, у которого есть хотя бы один турнир (`ON DELETE RESTRICT`), запрещено — используется архивация (`archived`, блокирующая создание новых турниров и изменение состава при сохранении публичной истории).
- **Штат клуба (`club_user`):** глобальные роли не меняются (`guest` / `arbiter` / `admin`). В штат клуба с ролью `manager` или `arbiter` можно включать только активных пользователей с глобальной ролью `arbiter` или `admin`. У активного клуба всегда есть минимум один активный `manager` (снять последнего менеджера нельзя). Менеджер клуба редактирует карточку/логотип клуба и управляет судьями (`arbiter`) и шахматистами своего клуба.
- **Турниры и изоляция прав:** каждый турнир создаётся строго в рамках активного клуба (`tournaments.club_id NOT NULL`). Создавать турнир в клубе могут `manager` этого клуба и `admin`, назначая судью турнира из штата этого клуба (или `admin`). Редактировать турнир, управлять его участниками, запускать, вести жеребьёвку/результаты, закрывать и экспортировать могут только назначенный судья турнира (`arbiter_id`), менеджер клуба этого турнира и глобальный `admin`; судьи чужих клубов получают `403`.
- **Единый реестр и открытые турниры (`club_player`):** реестр `players` и рейтинг Elo остаются едиными по всей системе. Шахматист может состоять в `0`, `1` или нескольких клубах; в турнир любого клуба можно заявить любого игрока из общего реестра (в том числе из других клубов или без клуба). Принимать и исключать шахматиста в конкретный клуб могут только `manager` этого клуба и `admin`.
- **Публичность, импорт и экспорт:** каталог `/clubs` и карточка `/clubs/{club}` публичны для всех посетителей. В импорте игроков доступна опциональная привязка загружаемых и сопоставленных как дубликаты игроков к выбранному клубу менеджера/`admin`. В экспорт протокола турнира (PDF/HTML/XLSX) добавляется клуб проведения.
- **Audit:** доменные события `club.created`, `club.updated`, `club.archived`, `club.restored`, `club.deleted`, `club.staff_changed`, `club.member_added`, `club.member_removed` пишутся в канал `audit`.
