## На разработку программы для расчета шахматного рейтинга

Предлагается разработать приложение, которое позволяет отображать списки шахматистов и их индивидуальных рейтингов, вводить результаты турниров с шахматистами из списков и обсчитывать новые рейтинги шахматистов.

## Функциональные требования

1. Добавление шахматистов
   a. Номер шахматиста
   b. Имя и фамилия
   c. Дата рождения
   d. Текущий рейтинг
   e. Дополнительная информация
2. Загрузка списков шахматистов из файлов (CSV, XLSX, ODS)
3. Отображение списка шахматистов
4. Изменение информации о шахматисте
5. Внесение информации о турнире
   a. Игроки и их результаты
   b. Название турнира
   c. Сроки проведения
   d. Дополнительная информация
6. Отображение списка турниров
7. Расчет личного рейтинга шахматиста (два режима: по среднему рейтингу соперников и по каждой партии; режим выбирается для турнира)
8. Экспорт списка шахматистов в PDF, XLSX, HTML
9. Экспорт таблицы турнира в PDF, XLSX, HTML
10. Отображение личной карточки шахматиста с графиком изменения рейтинга

## Нефункциональные требования

1. Web приложение, написанное на PHP + sqlite3 (Laravel).
2. Адаптивный интерфейс для просмотра информации на различных устройствах (мобильные телефоны, планшеты, десктопы).
3. Время отклика приложения не должно превышать 5 секунд.

## Целевая архитектура решения

### Слои и зависимости

```
HTTP: routes, middleware, controllers, Form Requests, Policies
        ↓
Application: Services, Actions, DTO
        ↓
Domain / Persistence: Eloquent models, scopes, observers
        ↓
SQLite
```

Правила:

- **Controllers** только принимают запрос, валидируют его через Form Request, проверяют право через Policy/Gate, вызывают Service/Action и возвращают view/redirect/response. Бизнес-логики, Elo-расчетов и многошаговых транзакций в контроллерах нет.
- **Services/Actions** содержат бизнес-логику: жеребьевку, расчет Elo, закрытие турнира, импорт/экспорт, управление пользователями. Они не используют `request()`, `response()`, `view()` и не зависят от HTTP-слоя.
- **Models** содержат связи, касты, scopes и небольшие инварианты. Многошаговые сценарии и транзакции — не в моделях.
- **Policies** отвечают за доступ; **middleware** — за аутентификацию, роли, блокировку пользователя, язык интерфейса и `request_id`.
- **Blade-шаблоны** отвечают только за отображение; расчеты и запросы к БД в них не выполняются.
- Зависимости направлены сверху вниз: HTTP → Application → Domain/Persistence. Обратных зависимостей нет.

### Правила транзакций и конкурентности

- Многошаговые изменения выполняются в `DB::transaction()` внутри Action/Service. Транзакции короткие; отправка почты, генерация PDF и HTTP-вызовы — вне транзакции.
- Для изменяемых агрегатов используется оптимистичная блокировка через поле `version` (`users`, `clubs`, `players`, `tournaments`, `tournament_participants`, `pairings`). Обновление — compare-and-swap: `WHERE id = ? AND version = ?`, затем `version = version + 1`.
- Если обновление затронуло 0 строк, выбрасывается `ConcurrentModificationException`; пользователь получает `409 Conflict` и локализованное сообщение из `lang/{en,ru}/errors.php` (см. `task_009`). Факт конфликта пишется в лог.
- `lockForUpdate()` не используется: SQLite не поддерживает построчные блокировки. Вместо этого — WAL, `busy_timeout` и короткие транзакции.
- Проверяются статусы: участники добавляются только в `draft`, результаты вводятся только в `in_progress`; экспорт турнира доступен в любом статусе, но для незавершенного турнира `rating_after` и итоговые места могут отсутствовать.
- Вставки защищены уникальными индексами (`users.email`, `tournament_participants[tournament_id, player_id]`); `QueryException` обрабатывается как `409`/`422`.
- Импорт шахматистов выполняется чанками по 100–500 строк, каждый чанк — в своей транзакции; частичный успех допускается, ошибки отдельных строк не откатывают уже загруженные чанки (см. [`questions.md`](questions.md#11-импорт-шахматистов-атомарность-и-частичный-успех)).
- Чтение файла и генерация PDF/XLSX/HTML выполняются вне транзакции записи: в транзакции только запись в БД.

### Целостность рейтинговой истории

- Рейтинговая история неизменяема: записи `ratings` не редактируются и не удаляются вручную.
- Удаление шахматиста запрещено, если у него есть записи в `ratings` или участие в турнире в статусе `in_progress`/`completed`; разрешено удаление только при участии лишь в турнирах `draft`.
- Внешние ключи: `ratings.player_id` — `ON DELETE RESTRICT`, `ratings.tournament_id` — `ON DELETE SET NULL`, `tournament_participants.player_id` — `ON DELETE CASCADE`.
- Удаление турнира в статусе `completed` доступно только `admin` и требует подтверждения; записи `ratings` при этом сохраняются.
- Проверка выполняется одновременно в Policy и в сервисе; интерфейс показывает причину запрета, а не только скрывает действие.
- Основание: [`questions.md`](questions.md#9-удаление-шахматиста-и-целостность-рейтинговой-истории).

### Язык интерфейса и данных

- Поддерживаемые локали — `en` (по умолчанию) и `ru`; список — в `config/locales.php` (`supported`), `APP_LOCALE=en`, `APP_FALLBACK_LOCALE=en`.
- Выбор языка выполняет middleware `SetLocale` в группе `web`: сессия → cookie `locale` (1 год) → `en`; неизвестное значение откатывается к `en`. Префикс языка в URL не используется, переключение — `GET /locale/{locale}`.
- Строки интерфейса, валидации, flash-сообщений, ошибок и писем — в `lang/en` и `lang/ru` (+ `lang/*.json`); устаревший путь `resources/lang` не используется.
- Пользовательские данные (ФИО, названия турниров, примечания) не переводятся. Машинные значения (статусы, `average`/`per_game`, коды ошибок, заголовки XLSX/CSV, audit-логи) остаются латиницей.
- Кодировка импортируемых CSV определяется явно (UTF-8 по умолчанию, Windows-1251 — при необходимости) и указывается в отчёте об импорте; локаль интерфейса на кодировку не влияет.
- PDF/HTML-подписи локализуются по языку запроса; даты форматируются по локали; расчёты, рейтинги и права от языка не зависят.
- `users.locale` не вводится: язык письма определяется языком инициатора действия (ограничение, см. `task_009`).
- HTML зависит от cookie, поэтому прокси/CDN не кэширует HTML без `Vary: Cookie`.
- Основание: [`questions.md`](questions.md#10-язык-интерфейса-и-данных) (пересмотр 2026-11-16), реализация — `task_009`.

### Логирование и ошибки

- Middleware `AssignRequestId` добавляет `request_id`; через `Log::withContext()` в каждый лог попадают `request_id`, `user_id`, `tournament_id`, `player_id` (если применимо).
- Каналы: `stack`/`daily` — приложение; `audit` — доменные события: смена роли, блокировка пользователя, импорт, завершение турнира, изменение рейтинга.
- Audit-канал — отдельные файлы `storage/logs/audit-YYYY-MM-DD.log`, не таблица БД; формат записи — JSON (`timestamp`, `event`, `actor_id`, `target_type`, `target_id`, `request_id`, `context`); retention — 90 дней, ротация — в `task_000`.
- Формат записи: `timestamp`, `level`, `event`, `request_id`, `user_id`, `message`, `context`. В production — JSON или line-формат с контекстом; `APP_DEBUG=false`.
- Ошибки валидации — через Form Requests и стандартные `422`; ошибки доступа — `403`; конфликты — `409`; отсутствующие сущности — `404`.
- Для Blade-интерфейса — единый layout ошибок и flash-сообщения. Для будущего JSON/API — единый конверт `{ "message": "...", "code": "...", "errors": {...} }`.
- Доменные исключения (`DomainException`, `ConcurrentModificationException`) маппятся на HTTP-коды в обработчике; стек-трейсы не показываются пользователю в production.

Клубные роли (решение №14 в `questions.md`, реализация — `task_010`):
- Глобальные роли не меняются (`guest`, `arbiter`, `admin`). Связь пользователя с клубом хранится в `club_user` с ролью внутри клуба: `manager` (менеджер клуба) или `arbiter` (судья клуба); назначать в штат клуба можно только активных пользователей с глобальной ролью `arbiter` или `admin`.
- У активного клуба всегда есть минимум один активный `manager`. Создавать турниры в клубе могут `manager` этого клуба и `admin`; вести турнир (редактирование, состав, старт, жеребьёвка, результаты, закрытие, экспорт) — назначенный судья турнира (`arbiter_id`), `manager` этого клуба и `admin`. Судьи чужих клубов получают `403`.

## Расчет рейтинга

### Между шахматистами

Пусть $R\_A$ - рейтинг шахматиста A, $R\_B$ - рейтинг шахматиста B. Тогда ожидаемое количество очков $E\_A$ из N партий, набираемых шахматистом A, можно рассчитать по формуле:

$$E\_A = \\frac{N}{1 + 10^{(R\_B - R\_A)/400}}$$

Если шахматист A набирает $S\_A$ очков, то его новый рейтинг $R\_A'$ можно рассчитать по формуле:

$$R\_A' = R\_A + K \\cdot (S\_A - E\_A)$$

где $K$ - коэффициент, определяющий, насколько сильно изменится рейтинг.

Значения $K$ могут быть следующими:

* Для игроков с рейтингом 2400 и выше: $K=10$
* Для игроков с рейтингом до 2400: $K=20$
* Для игроков, сыгравших менее 30 партий: $K=40$
* Для игроков, младше 18 лет с рейтингом до 2300: $K=40$

### В турнире

Рейтинг шахматиста в турнире считается по его результатам в этом турнире. При создании турнира выбирается один из двух режимов расчета (`rating_mode`):

* **`average` — по среднему рейтингу соперников.** Режим по умолчанию. Вычисляется средний арифметический рейтинг соперников, после чего применяется формула Elo ко всем партиям турнира.
* **`per_game` — по каждой партии.** Ожидаемые очки рассчитываются отдельно для каждой партии, затем суммируются. Режим точнее, так как не заменяет рейтинги соперников их средним значением.

В обоих режимах используются:

* $R_{before}$ — рейтинг игрока, зафиксированный на старте турнира; используется для всех партий, порядок партий не влияет на результат;
* $R_{opp\_before}^{(i)}$ — рейтинг соперника в партии $i$, зафиксированный на старте турнира;
* $N$ — количество завершенных партий против реальных соперников; bye, партии без результата и `0-0` не учитываются;
* $S$ — фактически набранные очки в этих партиях;
* $K$ — коэффициент, определяемый по правилам выше; рассчитывается один раз на турнир и применяется ко всем партиям.

#### Режим `average`

Средний рейтинг соперников:

$$R_{avg} = \frac{1}{N} \sum_{i=1}^{N} R_{opp\_before}^{(i)}$$

Ожидаемое количество очков:

$$E = \frac{N}{1 + 10^{(R_{avg} - R_{before})/400}}$$

Новый рейтинг:

$$R' = \operatorname{round}(R_{before} + K \cdot (S - E))$$

#### Режим `per_game`

Для каждой партии $i$:

$$E_i = \frac{1}{1 + 10^{(R_{opp\_before}^{(i)} - R_{before})/400}}$$

где $S_i = 1$ при победе, $0.5$ при ничьей и $0$ при поражении. Суммарные значения:

$$E = \sum_{i=1}^{N} E_i, \qquad S = \sum_{i=1}^{N} S_i$$

Новый рейтинг:

$$R' = \operatorname{round}(R_{before} + K \cdot (S - E))$$

**Примечания:**

* Режим расчета выбирается при создании турнира; до старта его можно изменить, после старта — нельзя.
* Партии `0-0` (обоюдная неявка) не включаются в расчет рейтинга, но сохраняются в турнирной таблице с 0 очков.
* При `games_per_round = 2` каждая партия учитывается отдельно.
* Если $N = 0$ (игрок не сыграл ни одной партии), рейтинг не изменяется.
